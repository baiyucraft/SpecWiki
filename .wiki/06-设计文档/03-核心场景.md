# 核心场景

> 状态：第一版核心场景草案
> 范围：第一版 9 个核心用户故事

## 1. 文档目的

本文档记录第一版必须优先支撑的 9 个核心用户故事。

这些故事共同描述了当前产品的第一条完整闭环：

```text
理解项目
-> 读取规则
-> 找到入口
-> 分析影响
-> 实施改动
-> 更新知识
-> 沉淀经验
-> 处理冲突
-> 主动声明规范
-> 协作恢复本地 runtime
```

## 2. 模板说明

本文件中的每个场景统一采用以下模板：

- 用户故事
- 用户价值
- 触发条件
- 前置条件
- 核心输入
- 系统行为
- 期望输出
- 成功标准
- 边界与暂不决定事项

## 3. 场景 1：`init` 后，用户能快速理解项目概览

### 用户故事

作为一个刚进入仓库的用户，我希望在执行 `init` 之后，能快速知道这个项目是做什么的、主要结构是什么、核心模块和入口在哪里，这样我不用先硬啃源码也能建立整体认知。

### 用户价值

- 降低进入陌生仓库的门槛
- 帮助用户建立第一版全局心智模型
- 为后续提需求给 Agent 提供共同上下文

### 触发条件

- 用户首次接触某个仓库
- 用户切换到一个不熟悉的仓库
- 用户在正式让 Agent 工作前，先想获得整体认知

### 前置条件

- 仓库可被扫描
- `init` 能完成基本分析

### 核心输入

- 仓库根目录
- 当前代码结构
- 可用的 facts/index 结果

### 系统行为

- 扫描仓库并建立基础索引
- 识别项目的高层定位
- 提取主要模块、目录和入口点
- 组装一份面向人阅读的概览结果

### 期望输出

- 一份可读的项目概览
- 粗粒度模块/目录结构
- 核心入口点
- 主要技术栈
- “建议从哪里开始看”的提示

### 成功标准

- 用户不用通读大量源码，也能建立初步认知
- 输出以“人容易读懂”为优先
- 结果足以支撑后续继续提问或继续让 Agent 工作

### 边界与暂不决定事项

- 本场景偏向人读概览，而不是 Agent 优先消费的纯结构化结果
- 本场景关注“快速理解”，不追求完整架构真相

## 4. 场景 2：Agent 写代码前，先读取代码风格和项目约定

### 用户故事

作为一个让 Agent 帮我写代码的用户，我希望 Agent 在动手之前，先读取并遵守项目已有的代码风格和项目约定，而不是按它自己的默认习惯生成代码。

### 用户价值

- 提高 Agent 输出与仓库风格的一致性
- 降低“能跑但不符合项目习惯”的结果
- 减少后续因风格和约定不一致产生的返工

### 触发条件

- 用户让 Agent 实现一个功能
- 用户让 Agent 修改现有代码
- 用户让 Agent 重构某个模块
- 用户让 Agent 修复一个问题

### 前置条件

- 仓库中存在可读取的代码风格和项目约定
- 系统能够根据任务范围匹配适用规则

### 核心输入

- 用户任务描述
- 当前任务的作用范围
- 仓库级规则
- 模块级规则

### 系统行为

- 判断任务属于哪个范围
- 提取该范围内适用的代码风格和项目约定
- 在真正生成代码前，将这些规则提供给 Agent

### 期望输出

- 当前任务适用的代码风格
- 当前任务适用的项目约定
- “该做什么 / 不该做什么”的约束
- 每条规则的作用范围和来源

### 成功标准

- Agent 生成的代码更符合项目已有习惯
- Agent 不会随意引入自己的默认风格
- 用户能理解 Agent 为什么这样写

### 边界与暂不决定事项

- 本场景重点约束的是“代码风格 + 项目约定”
- 这些规则不是普通页面搜索结果
- 如果 Agent 在开工前发现规则冲突，不能静默继续执行

## 5. 场景 3：Agent 开工前，先找到正确的改动入口

### 用户故事

作为一个给 Agent 提需求的用户，我希望 Agent 在开始改代码前，能先找到最可能正确的改动入口，包括相关文件、模块、符号和入口点，这样它不是盲改。

### 用户价值

- 提高第一次命中正确改动位置的概率
- 降低 Agent 在仓库里盲目游走的成本
- 为后续影响分析和代码修改建立可信起点

### 触发条件

- 用户给出一个功能需求
- 用户问“应该先改哪里”
- 用户让 Agent 在一个陌生区域里动手

### 前置条件

- 仓库已经建立基础索引
- 系统能对任务描述做初步定位

### 核心输入

- 用户任务描述
- 可选的函数名、路径片段、模块提示
- 当前索引结果

### 系统行为

- 从任务描述中抽取定位线索
- 匹配候选文件、符号、模块和入口点
- 给出候选结果及其相关理由

### 期望输出

- 候选文件
- 候选符号
- 候选模块
- 相关入口点
- 每个候选的理由和置信度

### 成功标准

- Agent 能从一小组高概率位置开始工作
- 定位结果主要依赖事实和图关系，而不是空泛摘要

### 边界与暂不决定事项

- 本场景首要结果应是事实级定位结果，而不是页面链接
- page 可以辅助，但不应成为主要入口

## 6. 场景 4：Agent 改代码前，先分析影响范围

### 用户故事

作为一个要修改已有代码的用户，我希望 Agent 在动手之前，先分析这次修改会影响哪些调用链、文件、模块和边界，这样能减少误伤和连锁问题。

### 用户价值

- 降低修改共享代码时的风险
- 提前暴露潜在波及面
- 帮助用户和 Agent 选择更稳妥的实施路径

### 触发条件

- 用户要做重构
- 用户要改一个共享方法
- 用户要删除或替换一个已有模块
- 用户问“改这里会影响什么”

### 前置条件

- 仓库已有可用的符号图、关系图或模块关系

### 核心输入

- 目标符号、文件或模块
- 调用关系、依赖关系、模块关系
- 相关项目约定（如果存在）

### 系统行为

- 跟踪上下游影响
- 分析调用链波及范围
- 汇总受影响的文件、符号、模块
- 发现关键边界风险时给出提示

### 期望输出

- 受影响的符号
- 受影响的文件
- 受影响的模块
- 调用链摘要
- 风险提示

### 成功标准

- Agent 不会盲目修改共享代码
- 影响分析主要建立在图关系证据上

### 边界与暂不决定事项

- 本场景是“改前分析”，不是“改后补救”
- 输出中可以引用约定，但主干仍然应是 facts/graph

## 7. 场景 5：新功能完成后，通过 `update` 更新相关知识

### 用户故事

作为一个完成了新功能开发的用户，我希望系统能在手动触发或自动识别后，更新与这次功能相关的项目知识，避免知识系统越来越过时。

### 用户价值

- 让知识系统随代码变化持续演进
- 降低“代码已经变了，知识还停在旧状态”的风险
- 为后续用户和 Agent 提供更新后的上下文

### 触发条件

- 用户手动触发 `update`
- 系统自动识别到一项有意义的新功能改动
- 某个功能分支或 PR 引入新的能力

### 前置条件

- 系统能够识别本次变更影响到的范围
- 系统能够对相关知识对象执行刷新

### 核心输入

- 变更后的代码事实
- 变更范围
- 可选的任务或 PR 上下文

### 系统行为

- 判断本次变更影响了哪些知识范围
- 对相关知识执行更新
- 记录更新来源和时间

### 期望输出

- 与该功能相关的知识得到更新
- runtime 状态得到刷新
- 必要时更新对外展示结果

### 成功标准

- 项目知识不会长期落后于真实代码
- 用户不需要手工维护大量 Markdown 文档

### 边界与暂不决定事项

- 本场景目前只确认“更新相关知识”
- 这里暂时不写死最终更新的是 page 还是 record
- “有新功能”不等于“必须长出很多新页面”

## 8. 场景 6：修复 bug 后，将经验沉淀为避坑记录

### 用户故事

作为一个刚修完 bug 的用户，我希望能把这次问题的现象、根因、修复方式和避免方式沉淀下来，方便以后的人和 Agent 在遇到类似问题时能快速复用。

### 用户价值

- 把一次性的踩坑成本变成可复用经验
- 降低同类问题重复发生的概率
- 让 Agent 在未来类似任务中能主动规避已知坑点

### 触发条件

- 某个 bug 被修复
- 发现了较难定位的根因
- 某类错误在项目中重复出现

### 前置条件

- 本次 bug 已经完成定位和修复
- 至少能说明问题现象和修复结论

### 核心输入

- 问题现象
- 根因
- 修复方式
- 避免方式
- 相关范围

### 系统行为

- 先将该经验沉淀为避坑记录
- 将记录绑定到相关模块、文件或符号
- 在未来相似场景中可被检索和复用
- 当结论被重复验证且适用范围稳定时，可进一步升级

### 期望输出

- 一条避坑记录
- 相关范围绑定
- 必要时形成故障排查类投影
- 在满足条件时，可升级为项目约定或规范

### 成功标准

- 后续类似问题出现时，能快速命中这条经验
- 系统不会把每一个 bug 都直接上升为全项目规范

### 边界与暂不决定事项

- 默认先沉淀为“避坑记录”
- 必要时再升级为“项目约定”或“规范”
- 不是每一条 bug 经验都必须升级

## 9. 场景 7：当规范与现实代码冲突时，系统要显式处理冲突

### 用户故事

作为一个依赖项目知识来驱动 Agent 的用户，我希望当系统发现“项目规范这么说，但现实代码不是这么做”时，能明确提示冲突，并进入处理流程，而不是悄悄选一边。

### 用户价值

- 避免 Agent 盲从过时规则
- 避免 Agent 无视项目既有约束
- 帮助用户看清“事实”和“期望”之间的差异

### 触发条件

- Agent 在开工前读取规则时发现冲突
- `update` 发现现有代码违反项目约定
- 新证据显示某条旧规则可能已经失效

### 前置条件

- 系统同时掌握规则侧和事实侧证据

### 核心输入

- 冲突规则
- 现实代码证据
- 适用范围
- 可选的变更上下文

### 系统行为

- 显式识别冲突
- 展示双方证据
- 给出当前暂定状态
- 进入后续治理或确认流程

### 期望输出

- 冲突记录
- 双方证据
- 当前状态
- 下一步建议动作

### 成功标准

- Agent 不会盲目服从过时规则
- Agent 也不会静默忽略项目记忆
- 用户能看见冲突是什么、为什么冲突

### 边界与暂不决定事项

- 声明型知识不等于客观事实
- 客观事实也不等于团队期望
- 冲突必须进入治理流程，不能静默覆盖

## 10. 场景 8：用户可主动向 wiki 增加规范，例如注释规范

### 用户故事

作为一个维护项目规则的用户，我希望即使某条规范不是从代码变更中自然提炼出来的，我也能主动把它加入 wiki 体系，例如注释规范、命名规范或 review 约定，这样后续的人和 Agent 都能按这条规则工作。

### 用户价值

- 让团队规则不必依赖“先写出代码再反推”
- 支持把明确共识直接沉淀为长期知识
- 让 Agent 在未来写代码时能提前读取并遵守

### 触发条件

- 用户决定新增一条项目规范
- 团队讨论形成了新的约定或政策
- 某类规则需要在未来被持续执行，但当前代码中尚未自然体现

### 前置条件

- 系统提供“主动声明规范”的入口
- 规范可以被绑定到明确作用范围

### 核心输入

- 规范标题
- 规范类型，例如 guideline / convention / policy
- 作用范围，例如全仓库、某语言、某模块、某目录
- 规则内容
- 可选的正例、反例、原因说明、执行方式

### 系统行为

- 将该规范写入正式的知识记录，而不是只修改某个页面文本
- 为该规范生成可供人和 Agent 快速消费的摘要
- 刷新 wiki 中对应的规范入口页、规范区块或规范索引
- 让后续 query 和 Agent 生成流程可以命中这条规范

### 期望输出

- 一条新的规范记录
- 一份规范摘要
- wiki 中可见的规范更新结果
- 后续 Agent 可消费的规则输入

### 成功标准

- 用户明确感知“wiki 已更新”
- 规范不仅能被人看到，也能被 Agent 在后续任务中实际消费
- 该规范不依赖某次代码变更才能进入系统

### 边界与暂不决定事项

- 本场景属于主动声明型知识写入，不属于代码变更触发的 `update`
- 默认应先写入结构化规范记录，再刷新页面或索引等可见投影
- 此类规范的后续废弃、替代和状态流转需要单独的生命周期管理

## 11. 场景 9：A 用户已生成并提交 wiki，B 用户拉取后可基于上库内容恢复本地 runtime

### 用户故事

作为一个协作开发中的用户，我希望当其他人已经完成 `init` 或 `update` 并把 `.wiki` 的正式产物提交到仓库后，我在拉取最新代码时，系统能基于这些已上库内容恢复本地的运行时和缓存，而不是要求每个用户都从零全量重建一遍。

### 用户价值

- 降低多人协作时重复初始化和重复计算的成本
- 让 `.wiki/.cache/` 真正成为可重建的派生层，而不是隐性主存储
- 让新拉取代码的用户尽快进入可 query、可继续 update 的状态

### 触发条件

- A 用户已经执行过 `init` 或 `update`
- A 用户将 `.wiki/.knowledge/`、`.wiki/wiki.metadata.json`、`.wiki/*.md` 提交到了仓库
- B 用户拉取了最新代码
- B 用户本地不存在 `.wiki/.cache/`，或 `.wiki/.cache/` 需要重新建立

### 前置条件

- 仓库中已存在可读取的 `.wiki/.knowledge/`
- 仓库中已存在可读取的 `.wiki/wiki.metadata.json`
- 仓库中已存在可读取的 `.wiki/*.md`
- 系统具备从正式产物反向恢复本地 runtime 的能力

### 核心输入

- `.wiki/.knowledge/` 中的知识记录
- `.wiki/wiki.metadata.json` 中的正式索引与状态信息
- `.wiki/*.md` 中的页面投影
- 当前本地仓库代码状态

### 系统行为

- 检查 `.wiki/.knowledge/`、`meta` 和 `page` 是否存在且可读取
- 基于这些正式产物恢复本地 `.wiki/.cache/`
- 重建 query 所需的本地运行时缓存、派生摘要和状态信息
- 如果发现当前代码与上库 wiki 产物不完全一致，则在恢复后标记状态并提示进一步同步或增量更新

### 期望输出

- 可用的本地 `.wiki/.cache/`
- 可 query 的本地运行时状态
- 当前状态提示，例如 ready / stale / needs_update
- 在需要时给出后续 `sync` 或 `update` 建议

### 成功标准

- B 用户拉取代码后，不需要强制重新全量 `init`
- 系统可以仅依据已上库的 `.knowledge`、`meta`、`page` 恢复本地派生层
- `.wiki/.cache/` 仍然保持“可重建、不上库”的定位

### 边界与暂不决定事项

- 本场景强调的是“恢复本地 runtime”，不是“重新生成正式知识本体”
- `.wiki/.cache/` 不是正式真相源，只是本地派生层
- 若当前本地代码比已上库 wiki 更新，系统应允许恢复后再进入增量校正流程
