# Repo Wiki 3.0 产品基线与设计治理

## 基线身份

`Repo Wiki Design 3.0` 是当前 canonical architecture baseline，稳定标识为 `repo-wiki-design-3`。它定义 Repo Wiki Core + Agents 的产品目标、适用范围、设计治理和完成判定，不等同于任何 semver release 或单个 package / crate 版本。

## 产品范围

产品目标是为本地代码仓库提供可持续更新、可查询、可审计的项目知识运行时，并让人和 Agent 共享同一层长期知识。当前架构以 `wiki-model / wiki-index / wiki-knowledge / wiki-runtime` 四个 core crate 和薄宿主 `Agents` 为边界。

宿主产品基线采用 Codex-first：Codex 是唯一 `reference host` 和首要兼容目标；Claude、CodeBuddy 是 `compatible host`。这个角色只决定宿主投影和验收优先级，不改变 Runtime authority，也不把 Codex 私有机制写入共享业务合同。CodeBuddy hooks/settings 属于次级兼容能力，不决定公共架构。

本基线不承诺所有未来场景已经实现，不把设计采纳等同于实现、验证或发布，也不要求产品 release、npm package 和 Rust crates 使用相同版本号。

## Authority 职责边界

- `05-产品基线与设计治理.md` 唯一负责 baseline identity、产品范围、版本域、状态证据和设计完成规则。
- `00-总体设计.md` 负责四包架构、主链、核心原则和场景映射；出现版本、状态或完成判定问题时回到本页。
- `01-Runtime设计.md`、`02-Agents设计.md` 和场景文档继续在各自范围内负责专题设计，不重复定义产品级治理规则。
- `02-Agents设计.md` 负责 reference/compatible host 角色、真实资产落点和三层边界；`host-trigger-contract` capability 负责可执行 trigger 语义。任何兼容宿主页不得反向覆盖这两处 authority。

后续 Runtime、核心场景、可靠性生命周期、宿主触发和文档收口五个合同 change 均以本页为产品级规范输入。

## 版本域与 Authority

每个版本域只授权自身 scope 内的问题。不同域可以独立演进，任何跨域关系都必须显式记录。

| 版本域 | 当前标识 | Authority | Scope |
| --- | --- | --- | --- |
| `architecture` | `repo-wiki-design-3` / `3.0` | 本页 | 产品目标、设计范围、治理规则和设计完成定义 |
| `product-release` | `v0.2.0` | 对应版本化 release contract；当前版本标识由下方显式映射绑定主包 manifest | 该 release 的公开 CLI、平台和稳定合同 |
| `artifact` | `spec-wiki@0.2.0`、`wiki-model@0.1.0`、`wiki-index@0.1.0`、`wiki-knowledge@0.1.0`、`wiki-runtime@0.1.0` | 对应 `package.json` 或 `Cargo.toml` | 单个 source artifact 的版本声明 |

版本关系使用以下概念合同：

```text
VersionRelation
  from: domain + id
  relation: targets | implements-subset-of | distributed-by | contains
  to: domain + id
  scope: 关系适用范围
  evidenceRefs: 证明关系的源码、合同或报告
```

当前明确声明的关系：

| From | Relation | To | Scope | Evidence refs |
| --- | --- | --- | --- | --- |
| `product-release:v0.2.0` | `implements-subset-of` | `architecture:repo-wiki-design-3` | v0.2.0 只承诺当前 release contract 覆盖的 3.0 子集 | `.docs/release/v0-2-0.md`、本页 |
| `product-release:v0.2.0` | `distributed-by` | `artifact:spec-wiki@0.2.0` | 当前 Windows x64 主 CLI source artifact | `packages/spec-wiki/package.json`、`.docs/release/v0-2-0.md` |

只有 authority、scope 或显式 relation 冲突才构成设计漂移。数值相等不自动建立映射，数值不同不自动构成漂移。npm 主包与产品 release 当前存在显式分发映射，但 Rust crates 仍是独立 artifact，不存在默认 lockstep policy。

manifest 只证明 source tree 声明的 artifact version；它不证明 artifact 已构建、验证或发布。release contract 描述版本承诺，也不单独证明 registry、Git tag、binary checksum 或 staged publish evidence 已存在。

## 设计决策与交付证据

合同状态不是单一生命周期阶段。每个合同域使用一个正交向量：

```text
ContractStatus
  decisionStatus: proposed | adopted | superseded | withdrawn
  implementationEvidence: none | partial | implemented | not-applicable
  verificationEvidence: none | partial | passed | failed | not-applicable
  releaseEvidence: none | planned | released | not-applicable
  evidenceRefs: 按证据轴分别记录可核验引用
```

`adopted` 只表示该设计在声明 scope 内是当前 authority。`implemented`、`passed` 和 `released` 必须分别提供对应 evidenceRefs；implementation、verification 和 release 三个证据轴互不推导，也不能由 decisionStatus、版本号或文档存在性推导。

| 可表达的事实 | 状态组合示例 | 含义 |
| --- | --- | --- |
| 已采纳但未实现 | `adopted + none + none + none` | 设计是当前 authority，尚无实现、验证和发布证据 |
| 已实现但未验证 | `adopted + implemented + none + none` | 实现证据存在，不能宣称验证通过或已发布 |
| 已验证但未发布 | `adopted + implemented + passed + none` | 实现与验证证据存在，仍无发布证据 |

`superseded` 或 `withdrawn` 不删除历史证据，只停止对应决策作为当前 authority。`.spec/archive/**` 可以作为 evidenceRefs，但归档事实本身不自动提升任何交付证据轴。

## 设计完成规则

### 单合同域设计完成

单个合同域只有同时满足以下条件，才能声明“设计完成”：

1. `decisionStatus=adopted`。
2. 存在唯一 authority，并明确适用范围。
3. 目标、非目标和依赖明确。
4. 可验证条件明确，已知冲突已有处置或责任归属。
5. 对应设计 change 的 full review 与 verification 证据通过。

单域设计完成只确认设计合同已采纳且可验证，不要求产品实现或发布完成。implementation、verification 和 release evidence 仍按各自证据轴报告。

### Repo Wiki 3.0 全项目设计完成

全项目设计完成必须同时满足：

1. parent 下六个 child 均满足单域设计完成规则并已实际归档。
2. 每个 child 的 authority、scope 和依赖关系不存在未处置冲突。
3. `documentation-closure` 已完成最终 authority、状态、引用和 INDEX 一致性门禁。
4. canonical baseline 不存在未处置的 blocking conflict。

不能用 active changes 为空、文件存在、首个 child 完成或某个版本号发布来替代上述证据。“设计完成”“产品已实现”“验证通过”和“产品已发布”必须分别报告。

## 稳定材料分类与后续责任

下表定义材料的长期角色和后续责任。本 change 只建立 canonical authority 和最小导航，不执行全库迁移。

| 材料范围 | 稳定角色 | 当前处理 | 后续责任 |
| --- | --- | --- | --- |
| `.wiki/06-设计文档/**` | 当前总体与专题设计 authority | 本页提供产品级治理；其它页面保留各自专题职责 | `documentation-closure` 修正状态标签、旧指针和交叉引用 |
| `.wiki/05-规格基线/capabilities/**` | capability 规格 authority | 不在本 change 补写 Purpose、改名或迁移 | `documentation-closure` 完成 capability 收口 |
| `.docs/release/**` | 版本化 release contract、gap 和历史发布面记录 | 保留为阶段 / 历史材料，不作为当前 architecture authority 或真实发布证明 | `documentation-closure` 决定稳定公开 release authority 的长期落点 |
| `packages/spec-wiki/package.json` | npm 主包 source artifact version authority | 保留为代码事实，并作为显式产品分发关系输入 | release 与 `documentation-closure` 检查映射和公开叙事 |
| `crates/*/Cargo.toml` | 各 Rust crate 独立 source artifact version authority | 保留独立版本，不建立默认 lockstep | 后续 release change 按实际发布策略声明关系 |
| `.docs/**` 中的 roadmap、design、quality 和 research | 阶段规划、迁移存根与分析材料 | 保留阶段属性，不提升为长期设计 SSOT | `documentation-closure` 清理失效 roadmap 与 authority 指针 |
| `.spec/archive/**` | 不可改的 change、review 和 verification 只读历史证据 | 保留原文，不作为当前 authority，不回写新结论 | 只允许当前 authority 通过 evidenceRefs 引用 |

后续五个合同 change 使用本页作为共同输入：

- Runtime / Query 合同消费版本域、authority 和状态证据规则。
- 核心场景验收消费单域完成与可验证条件。
- 可靠性生命周期消费 scope、非目标和 evidence 语义。
- 宿主触发合同消费 Runtime authority，不由宿主重定义产品状态。
- `documentation-closure` 执行最终全库状态、INDEX、capability、roadmap、引用和迁移收口。

当前 child 的验收不依赖上述全库收口已经完成。未迁移材料继续按本表归类，直到负责 child 提供 review 与 verification 证据。
