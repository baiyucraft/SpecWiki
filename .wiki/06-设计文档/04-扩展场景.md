# 扩展场景

## 1. 文档目的

本文档是 A1-A10 场景的当前分类 authority。`baseline` 表示当前正式合同已覆盖，`next` 表示已有 substrate 但尚未形成完整产品能力，`non-goal` 表示当前 repo-local 产品边界明确不承诺。

```text
scenario.A1 = baseline
scenario.A2 = next
scenario.A3 = next
scenario.A4 = baseline
scenario.A5 = next
scenario.A6 = baseline
scenario.A7 = non-goal
scenario.A8 = baseline
scenario.A9 = baseline
scenario.A10 = next
```

| 场景 | 分类 | 当前 substrate | 未覆盖边界 | 依赖 / 升级条件 |
| --- | --- | --- | --- | --- |
| A1 stale lifecycle | `baseline` | source/facts fingerprint、双轴 reliability、update/rebuild/restore | 不承诺旧结果 direct-trust | 所有公开 workflow 继续消费同一 assessment |
| A2 PR/review ingestion | `next` | declared authoring 与 governance evidence | 无 connector、采纳审批、merge decision ingestion | 独立 connector 与审批 change |
| A3 onboarding | `next` | overview、query、Agent 协作入口 | 无角色化进入流程或“禁区”产品模型 | 独立 onboarding 产品合同 |
| A4 query route | `baseline` | canonical Runtime Query | 本页不定义字段、排序或 route 状态机 | 服从唯一 Query authority |
| A5 richer monorepo impact | `next` | module/symbol/graph 与结构化模块命中 | 无完整 owner/entrypoint/callers/callees/impact traversal | Runtime Query 延期项完成 |
| A6 declared lifecycle | `baseline` | authority graph、authoring state、governance history | 无 hard purge 或自然语言自动裁决 | declared lifecycle capability |
| A7 ACL/visibility | `non-goal` | repo-local Git 边界 | 无身份、ACL、加密、远端 visibility authority | 需独立安全与身份模型，不从当前 runtime 推导 |
| A8 projection governance | `baseline` | eligibility、budget、lifecycle、protection、atomic commit | 无在线 usage ranking、redirect | projection policy 与 link evidence 保持确定性 |
| A9 failure/degradation | `baseline` | typed provider failure、production output gate、单值 action | development diagnostic 不等于正式成功 | 新 failure kind 必须接入同一 reducer |
| A10 incident model | `next` | health/governance evidence | 无 incident/timeline/recurrence/runbook 模型 | 独立故障复盘 capability |

## 2. 场景 A1：索引或知识变旧时怎么处理

用户切分支、拉取大改动或修改源码后，Runtime 以 live facts、formal snapshot 与本地 working state 生成统一 reliability assessment。Freshness 与 consumability 是两个正交轴：旧层可以在明确 provenance 下有限查询，但不得报告为 fresh/direct-trust；推荐动作按 `sync -> update -> rebuild -> init` 的证据优先级单值输出。

正式闭环是：

```text
fresh -> needs_update / stale -> update 或 rebuild -> fresh
```

formal artifact drift、source/branch drift 和 resume identity drift 都必须 fail closed；cache 存在不构成可消费证据。

## 3. 场景 A2：PR 或 review 结论自动沉淀

当前只有 declared authoring 与 governance evidence 可作为后续 substrate，不读取 PR/review、不自动采纳结论，也不替用户完成 merge decision。升级必须先定义 connector、来源 identity、审批、冲突与撤回合同。

## 4. 场景 A3：新成员或新 Agent onboarding

当前 overview、query 与 Agent 协作入口可辅助进入仓库，但不构成角色化 onboarding 产品。升级需要定义角色、必读顺序、禁止操作、完成状态与宿主一致性。

## 6. 场景 A4：查询路由

A4 已由 [06-Runtime查询合同](./06-Runtime查询合同.md) 唯一定义。本页只记录其 `baseline` 分类，不复制公开字段、路由闭集、排序、trust 或错误合同。

## 7. 场景 A5：多包或 monorepo 的跨模块改动场景

当前具备 module/symbol/graph substrate 和结构化模块命中，但 owner、entrypoint、callers/callees 与 impact traversal 仍是延期能力。多 workspace 事实存在不等于完整跨模块影响分析已交付。

## 8. 场景 A6：长期知识的生命周期

Declared record 的 semantic status、authoring state 与 authority group 分离：`active/deprecated/replaced` 不等于 `bound/missing/detached`。Replacement graph 必须得到唯一 head、无 head 或显式 conflict；block 消失保留 formal record，authority missing 要求治理复核，不能物理 prune。Authority、conflict 与 authoring 变化写入 append-only governance history。

## 9. 场景 A7：权限和知识可见性分级

当前只承诺 repo-local、Git-tracked 与本地 cache 的边界，不建立用户身份、ACL、私有笔记、加密或远端 visibility authority。A7 是明确 `non-goal`，不能由目录是否上库推导权限语义。

## 10. 场景 A8：少量稳定页面投影的治理

每个 KnowledgeUnit 都产生正式 projection decision，但只有 `required/selected` unit 形成 page plan；`knowledge_only` 不默认增殖页面。结构页必保留，domain leaf 使用稳定 budget，include/exclude/priority 是确定性 policy，hints 不改变 eligibility。

Demotion 先进入 `retiring`。Manual content、declared authoring block、manual inbound link 或不合法 managed link 会阻止 removal；clean page 才能在同一 runtime commit 中回收 page、digest、metadata 与 cache。Projection lifecycle 与技术 readiness 正交。

## 11. 场景 A9：工具链失败时的降级行为

Parser/index/formal artifact/provider/research/compose/assemble 失败必须保留 typed reason、remaining capability、evidence 与单值 action。Provider 的 unavailable、transport、timeout、tool error 与 context limit 不折叠为模糊成功；production 没有有效 provider output 时必须 blocked，structural seed 只允许 development diagnostic。

## 12. 场景 A10：更大规模的故障复盘与排查模式

当前 health signal 与 governance history 可提供 evidence，但没有 incident、timeline、recurrence、runbook 或独立故障模式模型。升级必须建立独立 identity、生命周期、查询与验收合同。

## 13. Compose、decomposition 与 provider session 边界

```text
compose_resume.granularity = knowledge_unit
compose_resume.current_unit = restart
provider_session.scope = request_local
provider_session.persistence = forbidden
decomposition.kind = deterministic_heuristic
decomposition.generic_typed_surface = not_complete
large_repository.full_compose = bounded_fixture_only
```

- 相同 workflow action、facts、稳定 knowledge tree 与 research contract 才能复用完整 research 和 draft/digest unit commit point。
- 任一 resume identity 维度变化都清除旧 working state；半写、错 unit/page/path、stale digest 或不匹配 pair 必须整 unit 重算。
- Provider session 只在一次 page research request 内有界存在。中断的当前 unit 从空 session 重启，session summary、turn 与 tool artifact ref 不写入 checkpoint、cache 或 formal artifact。
- Decomposition 是稳定 signal 与启发式 planner 的确定性结果，不代表已经形成覆盖任意代码库的通用 typed surface。
- 当前规模证据是 32-64 unit 的确定性中断 fixture，不是任意规模仓库的耗时或质量 SLA。

## 14. 维护规则

- 分类变化必须由独立 change 更新本页、直接相关 capability 与自动化合同测试。
- A4 的具体合同只修改 canonical Runtime Query authority。
- 历史 `.spec/archive/**` 是当时证据，不反向覆盖本页当前分类。
- 本页未使用 upstream；不存在直接迁移、改写或仅借鉴的外部实现。
