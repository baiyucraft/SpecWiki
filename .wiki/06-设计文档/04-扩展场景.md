# 扩展场景

> 状态：补充场景草案
> 范围：第一版之外的重要扩展场景

## 1. 文档目的

本文档记录那些“很重要，但不放进第一版 9 个核心场景里”的补充场景。

它们的作用是：

- 作为后续扩展方向
- 避免系统第一版就被做窄
- 提前保留未来设计边界

## 2. 当前补充场景清单

当前补充场景包括：

1. 索引或知识变旧时怎么处理
2. PR 或 review 结论自动沉淀
3. 新成员或新 Agent 的 onboarding
4. facts / knowledge / declared rules 的查询路由
5. 多包或 monorepo 的跨模块改动场景
6. 长期知识的过时、替代与生命周期
7. 权限和知识可见性分级
8. 少量稳定页面投影的治理
9. 工具链失败时的降级行为
10. 更大规模的故障复盘与排查模式

## 3. 场景 A1：索引或知识变旧时怎么处理

### 场景描述

用户切分支、拉取大改动，或者本地发生较大变更后，系统不能继续悄悄用旧数据回答问题。

### 为什么重要

如果不写这个场景，系统很容易出现：

- 看起来查到了结果
- 但其实是旧世界的结果

## 4. 场景 A2：PR 或 review 结论自动沉淀

### 场景描述

很多真正有价值的项目知识，不是在代码里产生的，而是在：

- PR review
- 架构讨论
- merge 决策

这些结论后续应支持转成可复用记忆。

### 为什么重要

如果忽略这个场景，系统最终只会记住“代码改了什么”，记不住“为什么这样改”。

## 5. 场景 A3：新成员或新 Agent onboarding

### 场景描述

一个新人或新 Agent 进入仓库后，不只是要看一份概览，还需要：

- 先看什么
- 先别碰什么
- 怎么安全进入项目

### 为什么重要

这个场景和 `init` 概览相近，但比概览更强调“进入项目的操作感”。

## 6. 场景 A4：查询路由

### 场景描述

同一句自然语言问题，背后可能应该走：

- facts 查询
- knowledge 查询
- declared rules 查询

系统后续应支持明确路由，而不是全部混在一起。

### 为什么重要

如果不写这个场景，后续 query 很容易继续依赖临时 prompt 和模型心情。

## 7. 场景 A5：多包或 monorepo 的跨模块改动场景

### 场景描述

一个需求可能同时影响多个 package、service 或 workspace。

系统需要处理：

- 多个候选入口
- 多个影响面
- 多套规则范围

### 为什么重要

如果不写这个场景，系统后面容易只适配单包仓库。

## 8. 场景 A6：长期知识的生命周期

### 场景描述

一条规则、一个避坑记录或一个项目约定，后续可能会变成：

- 已过时
- 被替代
- 不再适用

系统后续应支持这类生命周期。

### 为什么重要

否则知识只会越积越多，永远不下线。

## 9. 场景 A7：权限和知识可见性分级

### 场景描述

有些知识可能是：

- 仅本地可见
- 团队共享
- 可提交进仓库
- 不适合提交进仓库

### 为什么重要

如果不提前保留这个场景，后面很容易把公共知识和私有笔记混在一起。

## 10. 场景 A8：少量稳定页面投影的治理

### 场景描述

即使页面不是主本体，后续仍可能保留少量稳定页面，例如：

- 项目概览
- 架构地图
- 规范索引
- 故障排查索引

系统应能治理：

- 哪些页面值得长期存在
- 何时刷新
- 何时不应该继续增殖

### 为什么重要

否则页面膨胀问题很快会再次出现。

## 11. 场景 A9：工具链失败时的降级行为

### 场景描述

有时解析、建图或 LLM 相关流程可能失败。

系统后续应明确：

- 哪些能力还能继续工作
- 哪些能力只能部分可用
- 用户应该看到什么状态提示

### 为什么重要

静默的半失败，比明确的降级状态更危险。

## 12. 场景 A10：更大规模的故障复盘与排查模式

### 场景描述

有些 bug 不是一次性的坑，而是会逐渐演变成：

- 重复性的事故
- 成型的排查套路
- 一类结构化故障模式

### 为什么重要

这类场景比普通“避坑记录”更重，后续可能值得单独建模。
