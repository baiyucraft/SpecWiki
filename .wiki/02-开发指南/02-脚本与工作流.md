# 脚本与工作流

根级 `scripts/*.mjs` 只做 package 编排和分发 evidence 收集。Wiki、change、asset ownership 与路径安全规则必须留在 `packages/spec-wiki-lite/src/core`，避免脚本形成第二套业务判断。

## 主要入口

| 脚本 | 职责 |
| --- | --- |
| `scripts/run-tests.mjs` | 依次运行 package 测试、package 构建和根级 Vitest 合同测试 |
| `scripts/build-dist.mjs` | 构建 package，将发布文件 staging 到 `dist/spec-wiki-lite`，可选执行 `npm pack` |
| `scripts/tests/distribution.test.ts` | 校验 manifest、文件清单、tarball 安装与 CLI smoke |
| `scripts/tests/current-surface.test.ts` | 扫描当前源码和 Wiki，阻止已退出产品面的合同回流 |

## 编排规则

- 脚本通过子进程调用 package 自有的 `test` 和 `build`，失败码原样阻断根任务。
- staging manifest 只保留公开发布字段，不能携带 workspace 私有配置。
- 发布资产从 `packages/spec-wiki-lite/{bin,dist,assets}`、根 `README.md` 和 `LICENSE` 复制。
- package inventory 必须按相对 POSIX 路径排序，便于测试和 evidence 比较。
- `--pack` 只生成本地 tarball，本 change 不执行 npm publish、tag 或主分支合并。

## 业务边界

- CLI 和 core 返回结构化 domain result；脚本不重复解释 ready、valid 或 archive 条件。
- Markdown 与 YAML 解析使用 package 内的结构化 parser，不在脚本中用正则重建 schema。
- 文件路径必须经过公共 path guard；脚本不能绕过 guard 修改目标项目。
- current-surface 扫描排除 `.spec/archive/**`，历史证据不因当前产品收口而改写。

## 变更要求

- 新增公开文件时，同步 package `files`、staging 清单和 distribution test。
- 修改 CLI surface 时，同步 help、README、Wiki、Skills 和 current-surface test。
- 修改 stage 或 artifact 时，同步 core registry、测试、Skills 与自举 fixture。
- 一次性验证输出写入 `.tmp/` 或 change 报告，不写入长期 Wiki。
