# 代码注释规范

注释应补充类型和代码无法稳定表达的信息，不复述语句本身。

## 需要注释的内容

- 导出的 project operation、类型、常量和 CLI 入口；
- asset ownership、stage、artifact 与 issue taxonomy；
- 文件写入、原子 rename、归档和回滚边界；
- lexical/realpath containment 与 symlink 防护；
- YAML frontmatter、metadata 未知字段保留和 full/pass 判定；
- 退出码、错误分类和 human/JSON 输出约束。

## TypeScript 形式

导出接口、类型、函数和方法使用 JSDoc `/** ... */`。复杂文件可在顶部用短注释说明职责与明确不负责的内容。

注释按对象复杂度选择信息：

- 文件或模块：职责、输入、输出及不负责什么；
- 类型或字段：语义、取值闭集、默认值、空值和副作用；
- 函数或方法：参数、返回、错误、I/O 与调用前置条件；
- 复杂代码块：为什么需要该顺序，以及不能破坏的安全条件。

## 关键边界

涉及文件系统时，注释应解释安全意图，而不是重复 API 名称。例如：

```ts
/**
 * 将登记资产同步到项目根目录内。
 *
 * scaffold 与用户页面始终保留，managed 仅在 force 时更新，skill 始终跟随 package。
 * 所有目标必须先通过项目目录 containment 校验。
 */
export async function syncProjectAssets(
  projectRoot: string,
  options: AssetSyncOptions = {},
): Promise<AssetSyncReport> {
  // ...
}
```

阶段校验应说明单调 artifact 合同和阻断语义：

```ts
/**
 * 校验 active change 在当前 stage 已具备全部必需 artifact。
 * verification 只有在 review 与 test 报告均为 full/pass 时才可归档。
 */
export async function validateChange(
  projectRoot: string,
  changeId: string,
): Promise<ChangeValidationReport> {
  // ...
}
```

## 禁止项

- 不写“赋值”“调用函数”“返回结果”等逐行翻译。
- 不用注释掩盖命名、类型或模块职责问题。
- 不在注释中保留已删除架构和命令的 current 行为。
- 不把 proposal、讨论过程或一次性调试结论长期塞入源码。
- 不声称尚未实现的行为已经可用；待办必须绑定可追踪 change。

## 提交前自查

- 新导出入口是否说明真实职责、I/O 和错误边界。
- 新字段是否需要解释闭集、默认值或空值。
- 文件写入、路径解析和 archive 是否说明失败关闭条件。
- 注释是否与测试和当前 CLI 合同一致。
- 是否能通过更好的命名或类型删除解释性噪音。
