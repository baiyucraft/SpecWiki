# 代码注释规范

本页约束仓库内代码注释的最低标准。注释应补充代码无法稳定表达的信息，而不是复述代码本身。

## 目标

- 让公开契约、关键流程和跨模块边界可被维护者快速理解。
- 让字段语义、取值约束、默认行为和副作用不只存在于调用者经验中。
- 避免噪音注释、过期注释和逐行翻译代码。

## 适用范围

以下内容默认需要有稳定注释：

- 公开 API。
- 导出函数、导出类型和导出常量。
- 配置对象、默认配置和运行时配置。
- 状态结构、状态变更入口和派生状态。
- 生命周期、钩子、扩展点和插件入口。
- CLI 参数、命令选项和输出结构。
- 任务、流程、stage、artifact 等流程模型。
- 跨模块调用边界、兼容分支、恢复逻辑和错误分级。

## 语言注释形式

Rust 模块或文件级说明使用 `//!`，导出类型、字段、函数和方法使用 `///`。

TypeScript / JavaScript 文件级说明、导出接口、类型、函数和方法使用 JSDoc `/** ... */`。

注释结构按对象复杂度选择：

- 文件或模块：说明职责、上游、下游和不负责什么。
- 类型或字段：说明语义、所在层、取值约束、默认行为和空值含义。
- 函数或方法：说明职责、参数、返回、错误和关键副作用。

## 导出入口注释

导出函数、导出类型、状态变更入口、对外扩展点和 CLI 命令处理入口默认补 JSDoc。

注释至少说明以下一类真实信息：

- 这个入口负责什么。
- 不负责什么。
- 输入和输出的关键约束。
- 运行时副作用。
- 调用顺序或生命周期要求。
- 错误、恢复或兼容行为。

不要只写“处理数据”“执行操作”“返回结果”这类无法提供额外信息的注释。

## 字段级注释

对外导出的 `interface`、`type`、配置对象类型、参数对象、返回值类型，其属性默认补字段级注释。

字段注释至少提供一项真实信息：

- 语义。
- 取值约束。
- 单位。
- 枚举含义。
- 空值含义。
- 默认行为。
- 副作用。
- 兼容边界。

字段名已经能完整表达含义时，可以省略字段注释，但必须满足以下条件：

- 字段只在内部局部范围使用。
- 类型字面量、枚举命名或通用约定已经表达完整语义。
- 没有默认值、空值语义、单位、范围、副作用或兼容分支。

## 函数内部注释

函数内部存在关键步骤时，必须补充紧邻注释。注释应贴近对应代码，说明为什么这样做、边界在哪里、后续维护时不能破坏什么。

以下情况优先写紧邻注释：

- 关键决策。
- 状态切换。
- 副作用。
- 跨模块边界。
- 异常分支。
- 时序约束。
- 失效丢弃。
- 回写边界。
- 运行时恢复。
- 兼容处理。

禁止把函数内部注释写成逐行翻译。像“给变量赋值”“调用接口”“返回结果”这类可直接从代码读出的动作，不算合格的关键步骤注释。

## 禁止项

- 禁止只写“名称”“编码”“是否启用”这类复述字段名的噪音注释。
- 禁止用注释掩盖命名不清、职责混乱或类型设计不足。
- 禁止保留与当前实现不一致的过期注释。
- 禁止把历史背景、讨论过程或临时判断长期塞进代码注释。
- 禁止在注释中描述尚未实现的行为，除非明确标记为待办并绑定可追踪事项。

## 最低要求

- 文件职责清楚。
- 导出入口有稳定命名和职责说明。
- 公共契约字段默认有稳定、可读的字段注释。
- 关键副作用、运行时恢复和兼容处理有注释。
- 函数内部涉及时序、失效丢弃、回写边界、错误分级或跨模块约束的关键步骤有注释。

## 示例

```rust
pub fn run_init(repo_root: &Path) -> io::Result<InitReport> {
```


## 提交前自查

提交涉及代码的改动前，至少检查：

- 新增或修改的公开契约是否补充了必要注释。
- 新增字段是否说明了语义、约束、默认行为或空值含义。
- 新增关键流程是否说明了副作用、状态切换和异常分支。
- 注释是否仍然符合当前实现。
- 是否存在可由更好命名或类型设计替代的解释性注释。

本文参考通用项目注释规范整理，可按项目实际技术栈补充更具体的语言、框架或 API 注释规则。
