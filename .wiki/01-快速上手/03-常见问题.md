# 常见问题

## `spec-wiki init` 负责什么？

`spec-wiki init` 是 SpecWiki 的统一初始化入口，负责安装 Codex、Claude、CodeBuddy 等宿主资产，并触发 repo-local knowledge runtime 的初始构建。

实现内部仍可以把宿主 bootstrap、扫描、索引、knowledge runtime 构建拆成不同阶段，但用户侧不再把它们理解成两套初始化命令。

## 为什么文档优先使用 Codex？

Codex 是当前唯一 reference host，repo-local `.codex/skills/wiki-*/SKILL.md` 是首要兼容投影。Claude 与 CodeBuddy 仍受支持，但属于 compatible host；CodeBuddy 的 hooks/settings 只补充其宿主机制，不会反向改变共享 trigger、query 或 Runtime 合同。

## `--bridge-stdio` 是否等于可恢复 Agent 会话？

不是。基础 bridge forwarding 已存在，但 production `research_page` bridge 与完整 agent-session events 当前未启用。Provider session 只在单次 `research_page` 调用内有效，workflow resume 从 `session=None` 开始，禁止持久化 session summary、turns 或 tool refs。

## 为什么 `.wiki/` 里有长期文档，也可能有 runtime 产物？

`.wiki/` 同时承载两类内容：

- 长期文档：根入口、栏目索引、模块指南、对外方法等人工维护页面。
- runtime 产物：`.wiki/.knowledge/**`、`.wiki/.cache/**`、`wiki.metadata.json`，以及由 `.wiki/INDEX.md`、栏目 `INDEX.md` 和 `NN-主题.md` 组成的正式可见 Wiki 页面树。

两者不能混写。长期文档解释项目知识，runtime 产物由 `wiki-runtime` 生命周期维护。

## `pnpm run test` 失败但 `cargo test` 通过怎么办？

先看失败是否来自共享测试项目 fixture。当前部分脚本测试依赖 `tmp/test/storybook`、`tmp/test/dagger` 的状态；如果这些目录缺失或不是预期状态，会触发 reference report / analysis 断言失败。

## 什么时候更新 Wiki？

- 稳定开发规则、公开 CLI、配置边界、模块职责发生变化时，更新 `.wiki/`。
- 临时方案、review 明细和测试报告写入 `.spec/changes/**` 或 `.spec/archive/**`。
- runtime 页面和 cache 由 `spec-wiki init` 以及后续 `update / sync / rebuild` 维护动作更新。
