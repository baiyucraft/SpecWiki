## Context

当前仓库已经完成了第一阶段的工程外壳：`wiki-core` 与 CodeBuddy Agent 的调用链已可运行，`.wiki/` runtime 也具备最小写入能力。但现有生成结果仍以基础页面和最小索引为主，缺少稳定的模块树、模块边界和页面层级，因此无法把 Wiki 组织成“总览页 -> 架构页 -> 模块页”的结构，也无法为后续增量更新、结构化查询和更高质量的内容生成提供可靠输入。

`.wiki/06-设计文档/00-总体设计.md` 已明确将 `Hierarchical Decomposition` 作为 core pipeline 的关键阶段。本次变更就是把这一阶段从设计提升为可实现的中间层。

约束保持不变：

- 当前仍仅支持 Windows。
- 当前宿主仍仅支持 CodeBuddy Agent。
- 事实层保持 deterministic，不依赖 LLM。
- `query` 继续以 JSON 结构化输出为主，TOON 留到后续迭代。
- Git 元信息是可选增强，不是 `init` 和页面生成的硬前提。

## Goals / Non-Goals

**Goals:**

- 在 `Repository Scan` 之后建立稳定的 `ModuleTree`，表达模块边界、父子层级和跨模块关系。
- 让 `Page Planner` 基于模块结构生成层级化页面，而不是仅按目录或固定模板生成。
- 扩展 `wiki.metadata.json` 的导出内容，使其能够表达模块、页面层级和页面来源关系。
- 让 `init` 和 `query` 都开始围绕模块树工作，为后续增量更新和内容增强打下基础。
- 让 core 能在非 Git 目录上执行初始化，并在存在 Git 时补充分支、提交等元信息。

**Non-Goals:**

- 不在本次变更中引入 LLM 增强、TOON 输出或图示生成。
- 不在本次变更中实现真正的增量更新；`update` 的细粒度行为留到后续迭代。
- 不在本次变更中扩展新的宿主或平台。
- 不在本次变更中引入完整 AST 或 tree-sitter 解析体系，仍以启发式和配置驱动识别为主。
- 不在本次变更中实现 Git / SVN 的统一版本控制抽象；这会在后续迭代单独处理。

## Decisions

### 1. 用 `ModuleTree` 作为层级化理解的唯一事实入口

`Repository Scan` 继续负责收集文件、配置、入口和依赖线索，但不直接参与页面生成。扫描结果会先进入 `Hierarchical Decomposition`，生成 `ModuleTree`，再由 `Context Builder` 和 `Page Planner` 使用。

这样做的原因是：

- 避免页面规划直接依赖零散的扫描线索。
- 为后续 `query`、`update` 和 metadata 导出提供稳定中间模型。
- 将“仓库事实”和“页面组织”明确分层。

备选方案：

- 直接用目录树规划页面：实现更快，但无法稳定表达模块边界和跨模块关系。
- 直接让生成器从扫描结果推断模块：实现简单，但上下游边界不清晰，后续扩展成本高。

### 2. 第一版模块拆分继续走 deterministic 规则

模块拆分优先基于以下线索：

- workspace / package 边界
- 顶层目录聚类
- 入口文件
- 显式依赖提示
- 目录与配置约定

不在本次变更中引入 LLM 或重型语法分析。这样做是为了让 `ModuleTree` 可测试、可缓存、可重复构建。

备选方案：

- 直接引入 LLM 命名和拆分模块：产出可能更“聪明”，但不可重复，且难以支撑状态判断。
- 直接引入完整 AST 解析：理论上更精确，但当前成本过高，不适合作为这一迭代的交付边界。

### 3. 页面规划统一收敛到三类基础页面

第一版层级化页面规划只要求稳定产出三类页面：

- 项目总览页
- 系统架构页
- 模块页

其中模块页可以有父子层级，架构页和总览页引用模块树与跨模块关系。这样可以在不引入过多页面类型的前提下，让 Wiki 先具备结构感。

备选方案：

- 一次性引入更多专题页、流程页、部署页：信息密度更高，但需要更多上下文构建逻辑，会稀释本次变更目标。

### 4. `wiki.metadata.json` 继续由内部状态模型导出

本次不会让 `wiki.metadata.json` 成为内部主模型，而是继续沿用 `WikiState -> MetadataMapper -> WikiMetadataExport` 的方向，并新增以下信息：

- 模块列表
- 模块层级
- 页面层级
- 页面与模块、源码之间的来源关系

这样可以保证外部格式可演进，而内部模型仍服务于 pipeline。

备选方案：

- 直接在 metadata 上堆字段并让各模块直接读写：短期快，但会让内部状态模型失控。

### 5. `query` 直接消费模块结构，而不是只搜索页面文本

`query` 在这一迭代中必须能够返回：

- 命中的页面
- 相关模块
- 相关源码
- 层级化摘要或命中说明

实现上仍以 deterministic 检索为主，但输入应包含页面、模块和关系，而不是仅搜索 Markdown 文本。

备选方案：

- 继续只做页面文本匹配：实现简单，但无法体现本次新增的模块结构价值。

### 6. 版本控制信息降级为可选元数据

`init`、`Page Planner`、`Document Generator` 和 `metadata` 的核心写入流程都不应强依赖 `.git`。Git 信息只在存在时读取，不存在时使用可识别的空值或未索引状态。

这样做的原因是：

- Repo Wiki 的核心对象是本地代码目录，而不是某一种版本控制系统。
- 后续支持 SVN 时，才适合在上层增加统一的版本控制元信息抽象。
- 先把 Git 从硬前置降级，才能保证核心 pipeline 不与版本控制类型耦合。

备选方案：

- 继续要求必须存在 `.git`：实现简单，但会把核心能力错误绑定到 Git。

## Risks / Trade-offs

- [模块拆分规则过于保守] → 先保证稳定和可重复，再在后续迭代补充更强的结构识别。
- [metadata 字段扩展过快] → 只导出本次页面规划和查询必须使用的模块结构字段，不一次性塞入所有分析结果。
- [页面层级生成后内容仍偏薄] → 本次先解决结构组织，内容质量增强留给后续生成器与 LLM 迭代。
- [现有 query 逻辑与新模型并存期间复杂度上升] → 以 `PageContext` 和 `ModuleTree` 为唯一新增输入，避免出现并行查询路径。

## Migration Plan

1. 先扩展扫描后的中间模型，建立 `ModuleTree` 与相关 mapper。
2. 再调整 `Page Planner` 和 `Document Generator`，使其能消费模块结构并生成层级化页面。
3. 最后扩展 metadata 导出与 query 输出，并补齐对应测试。

如果实现过程中发现模块拆分规则不足以支撑稳定输出，应回退到“较粗粒度模块也能稳定输出”的方案，而不是引入临时的并行模型。

## Open Questions

- 模块页的最终标题是否完全使用目录/包名，还是允许引入受控命名规则。
- 跨模块关系在第一版 metadata 中导出到什么粒度最合适：仅模块级，还是同时包含页面级引用。
