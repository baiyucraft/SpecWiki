## Context

当前仓库已经具备可运行的 Rust core、CodeBuddy adapter 和一组最小测试，但交付链路仍存在三个明显缺口：

1. `scripts/stage-binaries.mjs` 仍以固定平台包名和固定版本常量生成产物，无法稳定反映真实包信息。
2. `scripts/build-core.mjs` 只定位 `target/debug` 下的本地二进制，更接近开发辅助脚本，而不是发布前 staging 输入。
3. 仓库缺少端到端测试与 README 说明，无法证明“从适配层调用 core 到生成 `.wiki/` 产物”的整条链路可复现。

这次 change 不扩展 Wiki 生成能力本身，而是收口已有能力的分发、验证和使用说明，使仓库达到“可打包、可验证、可交接”的状态。

## Goals / Non-Goals

**Goals:**
- 让主包与平台包的 staging 结构从真实包元数据推导，避免脚本中硬编码名称和版本。
- 为当前运行平台生成正确的二进制分发目录与 manifest，并保留后续扩展多平台的稳定接口。
- 增加覆盖 `init -> update -> query` 主链路的端到端测试，验证适配层与 Rust core 的集成行为。
- 补充 README，使开发者能够完成本地开发、测试、打包与发布前检查。

**Non-Goals:**
- 不在本次 change 中实现新的 Wiki 页面生成逻辑、增量算法或结构化查询协议。
- 不引入新的运行时桥接方式，例如 N-API、HTTP 服务或守护进程。
- 不一次性做完整 CI 发布矩阵；本次只定义本地 staging 和可验证约定。

## Decisions

### 决策 1：以 `packages/codebuddy/package.json` 作为主包事实来源

staging 过程将从 `packages/codebuddy/package.json` 读取包名、版本、bin 信息，再生成 `dist/npm/<main-package>/package.json`，而不是在脚本中重复维护常量。

原因：
- 减少发布元数据漂移，避免版本或包名在多个文件中失配。
- 主包本来就是用户安装入口，由它定义分发信息更自然。

备选方案：
- 在根目录 `package.json` 中维护发布元数据。放弃原因是当前根包是 workspace 容器，不是最终分发工件。
- 继续在脚本中写死常量。放弃原因是维护成本高，且容易在版本迭代中失真。

### 决策 2：平台包名与二进制目标路径由当前平台动态计算

staging 脚本将根据 `process.platform`、`process.arch` 和约定的 ABI 后缀生成平台包目录名，并拷贝对应平台的 core 二进制。第一版至少保证当前开发平台正确，接口上允许后续扩展更多目标。

原因：
- 当前实现将平台包写死为 `win32-x64-msvc`，无法表达实际运行环境。
- 设计目标是 npm 主包通过 `optionalDependencies` 装配平台包，平台命名必须稳定可推导。

备选方案：
- 一次性在本地生成所有平台包。放弃原因是当前仓库并没有现成的跨平台二进制输入，也会让本地验证复杂化。
- 只保留单包，把二进制直接放进主包。放弃原因是会显著增大主包体积，也偏离既定分发模型。

### 决策 3：端到端测试直接驱动已打包的适配层接口，而不是只测内部函数

新增的 e2e 测试将创建临时 Git 仓库，设置 `CODEBUDDY_WIKI_CORE_BIN` 指向本地构建的 core，可通过适配层公开接口完成 `init`、`update`、`query`，并断言 `.wiki/` 产物与返回结果。

原因：
- 现有单元测试和集成测试只能证明局部模块存在，不能证明真实调用链可工作。
- 直接测试适配层对 core 的调用，更接近最终用户使用模型。

备选方案：
- 只调用 Rust 二进制做黑盒测试。放弃原因是无法覆盖 adapter 的协议拼装与结果解析。
- 只 mock `invokeCore` 做 JS 侧测试。放弃原因是这类测试已经存在，但不能验证真正的跨语言边界。

### 决策 4：README 只覆盖可操作流程，不追求设计文档复写

README 将补齐安装、构建、测试、打包、`.wiki/` 目录说明和发布前检查，但不会重复 `docs/plans/` 中的架构设计。

原因：
- README 的目标是帮助开发和验证，不是保存完整设计推导。
- 将设计与操作文档分离，可避免长期重复维护。

备选方案：
- 把设计内容整体并入 README。放弃原因是会混淆“为什么这么设计”和“今天怎么运行”。

## Risks / Trade-offs

- [平台命名规则仍然不完整] -> 先把“当前平台可推导、命名规则集中管理”定稳，后续扩展其它平台时复用同一映射层。
- [e2e 测试依赖本地已构建二进制] -> 让测试显式校验二进制存在并给出清晰失败信息，避免隐式失败。
- [README 与脚本可能再次漂移] -> 文档以实际脚本入口为中心编写，并在任务中加入手动校对。
- [当前 `update` 仍是最小实现] -> e2e 只验证当前公开行为，不把未承诺的“真正增量更新”写进本次需求。

## Migration Plan

1. 统一主包 manifest 来源，调整 staging 脚本读取方式。
2. 抽出平台包名与二进制定位逻辑，更新 staging 测试断言。
3. 增加 e2e 测试夹具与运行入口，验证适配层到 core 的主路径。
4. 更新 README，补齐开发、验证和发布前流程。
5. 以现有测试和新增 e2e 作为验收基线；如 staging 结构变更导致脚本失败，可回滚到前一版脚本并保留新测试草稿。

## Open Questions

- 平台包命名是否需要在本次 change 中显式覆盖 `linux-musl` / `darwin-arm64` 等更多组合，还是先只约束当前平台与命名生成器。
- e2e 测试是直接 import `packages/codebuddy/src/index.ts`，还是先走打包后的入口脚本。当前更偏向前者，因为目标是验证适配层行为而非 npm 安装器。
