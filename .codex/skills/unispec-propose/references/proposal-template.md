# Proposal 模板

用于 `unispec-propose` 生成 `.spec/changes/<change-id>/proposal.md`。

Proposal 专注回答“为什么做”“做什么”“如何验收”“影响哪里”，不写“怎么做”。详细设计、接口、数据库、迁移步骤、实现任务和排期应 deferred 到后续 `design.md`、`system-tests.md` 或 `tasks.md`。

## 使用规则

- `proposal.md` 必须使用本文档中的固定二级标题。
- 三级标题和提示项按需使用；简单工程 change 不需要创建不适用的小节。
- 不适用的维度直接省略，不保留空表格、空标题或占位文本。
- 只保留会影响 scope、验收、风险或后续 design / plan 的信息。
- 本模板是 Skill 内部 reference，不是 change 的 research 产物；不要在 `proposal.md` 的 `参考资料` 中引用本文件。

## 写作边界

- `问题` 聚焦现状、触发因素、真实痛点，不写解决方案。
- `目标` 可以合并业务目标、用户价值和业务价值；不要为工程类 change 编造虚假的业务包装。
- `成功标准` 必须可验证，后续应能转化为 `system-tests.md`。
- `影响范围` 可以参考业务需求模板提炼角色、场景、范围、规则、数据、UI、集成和非功能期望，但只写业务层面的事实和约束。
- `数据需求` 不写数据库表结构、字段设计或迁移方案。
- `用户界面需求` 不写 UI 方案、布局细节或组件实现。
- `集成需求` 不写接口协议、鉴权流程或调用实现。
- `非功能期望` 写业务期望和验收指标，不写优化方案。
- `参考资料` 只引用 research 报告、用户输入、外部文档或相关 artifact，不引用本模板。

## 禁止事项

- 不把 proposal 写成完整 BRD / PRD 大文档。
- 不保留大段空表格、空标题或占位项。
- 不写架构设计、接口设计、数据库设计、迁移步骤、实现任务或排期。
- 不为了模板完整性扩大当前 change scope。
